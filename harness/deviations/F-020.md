## 2026-10-17 · F-020, F-021, F-022 · §7.7, §14

- **One current phone number per person.** When a LID is seen with a new PN (the person changed number), the old PN link is closed (`valid_to`), so the old number no longer matches them. DESIGN.md doesn't cover this case.
- **Bulk participant seeding never asks WhatsApp** (`EnsureKnown`). §7.7 says a PN-only person gets its LID looked up "immediately", but joining a 1,000-member phone-number group would fire 1,000 usync queries. Those persons gain their LID from SenderAlt or participant data later. The per-message path (`Ensure`) still looks up once, rate-capped in the connector (one per 3 s, burst 5; past the cap the lookup is skipped, not queued).
- **A recycled number raises no `Resolved` event**, so back-fill can't apply the old owner's number-based bans to the new owner (a contract assumption).
- **Memberships of a shared group are combined on merge**: earliest first-seen and join time, summed counts, highest role, flags OR-ed.
- **Unknown sources are rejected**, as §14 lists a closed set.

## 2026-10-17 · F-022 · §7.7 (Postgres merge, PR 2)

- **The Postgres merge re-points every column that refers to a person**: each single-column foreign key to `app.persons(id)`, plus each bigint column in schema `app` named `person_id`, `*_person` or `*_person_id`, found in the catalog, so tables later features add (strikes, detections, bans, corpus…) are covered without this package knowing them. The name rule exists because WP-I's `detections` and `group_bans` were created before `app.persons` without foreign keys; their migrations say the keys would be added "once the persons table exists (wp-f)", but WP-F doesn't add them, because WP-I's committed integration tests insert person IDs that don't exist in `app.persons`. Convention for later tables: a person column follows the name rule, and a column that must keep pointing at a merged-away record (history) must not. If re-pointing a row would duplicate one the surviving person already has (a unique constraint), that row is dropped, since the survivor's row stands for the same fact; the audit entry records how many were dropped per table.
- **The merged-away record is kept** with `merged_into` set and its identifiers cleared, so history (`person_merges`, old references) stays valid.
- **`ObserveSender` records a lone message sender with source `event`** (§14's source list has no "message sender" value).
