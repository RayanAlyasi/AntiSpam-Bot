## 2026-10-17 · F-088 · end-to-end fast lane (wp-l, integrating wp-a…wp-k)

- Built:
  - `internal/pipeline` with two layers. `Engine` is storage-free: textnorm.Prepare → the T0/T1
    analyzers → scoring.Classify → the AI verifier (gateway) for UNCERTAIN → wp-i's policy steps
    with wp-j's `safety.Decide`. `Pipeline` writes, in one transaction: claim, detection, local
    ban, queued revoke/kick, review item and its post.
  - `AnalyzerSet` (wp-g's keyword/regex/fuzzy/script/domain/exact/blacklist analyzers, plus the
    corpus near-duplicate matcher), `MemStore`, `ReviewActions`.
  - `internal/pipeline/pgstore` (tx-bound Postgres store over wp-i's PolicyStore.WithTx, wp-h's
    EnqueueTx and an ambient-transaction `Conn` for the review store).
  - `internal/pipeline/pipelinetest` (the harness: Postgres, the real executor drained on the fake
    clock, rules over the real store).
  - `internal/wa/adapter/synth` (constructed messages → real whatsmeow events → wp-b's builder).
  - `internal/wa/adapter/inboxenv` (inbox rows → envelopes).
  - `internal/app/fastlane`: the production lane per bot (executor, rules listener, AI,
    reviews), `Lanes` as the inbox's moderation sink, `Corpus` (near-dup index over
    corpus_entries), `CorpusLearning` (review ✅ / `.spam` → corpus entry; overturn → retract),
    `Reviews` (wp-k's review service and queue bridge), `IdentityMembers`.
  - `cmd/antispam`: the workers role runs the fast lane, the inbox moderates through it, and
    review timeouts and the AI cache purge run as River jobs.
  - `HASH_KEY` (config, env.example, compose, README). Migration 00034 `corpus_messages` + `corpus_allow`.
- Tests: every hidden acceptance test for F-088 and F-117 passes, plus unit tests for the engine
  and pipeline, and integration tests for pgstore, fastlane (shadow, NOTIFY blacklist reload,
  stored corpus, learning loop, inbox rows), the hash key, and the replay through Postgres.

### Follow-ups
- wp-k + wp-l, before F-114: after #39 there are two `review.Corpus` implementations,
  `fastlane.CorpusLearning` (wired; app.corpus_messages) and `review/pgstore.Corpus` (unwired;
  app.corpus_sources, which uses `Confirmation.Envelope`, ConfirmPattern and DecidedByPerson).
  Keep one implementation and one message→entry table, or an overturn handled by one misses
  entries the other confirmed.
- F-114: when the fast lane starts saving evidence snapshots (pipeline.Config.Evidence),
  `CorpusLearning.AllowFingerprint`'s no-entry path (learning.go, the f.Text branch) fingerprints
  the snapshot's already-masked text. Build the allow fingerprint from the text in its live form
  instead, or an overturned variant with a number stays known.
- The panic value is logged and stored in inbox.last_error as is; nothing builds a panic from
  message content today.
- The executor has no exported "never called" error class, so while a bot is disconnected a queued
  action counts as a call (wa.ErrTimeout). wp-h's Runner, which runs executors only for connected
  bots, removes this.
- whatsmeow's own logs: the connector (wp-f) owns the waLog bridge. Logging and metrics outside
  the pipeline boundary are the §16 audit follow-up.
- `.go-arch-lint.yml` is still in harness/proposed. When a human adds it, `internal/pipeline`,
  `internal/app/fastlane` and `internal/wa/adapter/{synth,inboxenv}` need components (the F-000
  judge already flagged the missing composition-root home).
- Trust and strikes (`review.Standing`) have no store yet, so an overturn doesn't restore trust.
- The groups table (wp-f) should say which groups are protected; the fast lane falls back to
  "has a settings document".
- Group settings need a default country (numbers in text) and an `ai.context` switch (F-108).
- Running `gofmt -w internal` reformats other packages' committed tests (the tamper audit catches
  it). Format only your own paths.
- Multi-bot: `Lanes` keeps one lane per bot, but reviews pick the bot for a review group from the
  groups table, or else the only connected bot.
