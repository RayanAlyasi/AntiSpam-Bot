# WP-L bundle: F-088, F-089, F-091, F-117

Four features in one build. Hidden acceptance tests exist only for the core features **F-088**
(`acceptance/pipeline/`, build tag `integration`) and **F-117** (`acceptance/neardup/` untagged, plus
`acceptance/pipeline/neardup_test.go`). The builder writes the tests for F-089 and F-091.
Sibling packages (envelope builder, normalize, detect, scoring, policy, actions, identity, inbox,
corpus/blacklist, review) are being built in parallel. The tests reach them only through WP-L's own
surface below, and the builder adapts that surface to the siblings.

## F-088 End-to-end fast lane: inbox to actions (core)
**Goal:** one inbox event → envelope → normalize → T0/T1 analyzers → scoring → band → routing →
a detection row plus enqueued actions, written in **one** Postgres transaction. The action executor
then performs the writes through `WAClient`.
**Behaviour** (Standard preset unless stated; what reaches WhatsApp after the queue drains):
- Known spam (confirmed corpus fingerprint, or a blacklisted number in a vCard `waid` or `TEL`) is
  CERTAIN/`known`. From a **new** member: Revoke + UpdateParticipants(Remove) + an active ban (rejoin
  block), route `auto_ban`. From an **established** member (pre-existing at onboarding): Revoke and a
  review Send to the review group, never a Remove, route `ask`. The band and source are the same for
  both senders (no trust bonus).
- Matrix per preset for text from a new member: Relaxed deletes only; Standard and Strict delete and ban;
  Ask admins (= `ask_delete_first`) deletes and reviews, never bans. `ask_before_action` sends a review
  only: no delete, no ban.
- A normal message makes no write calls and plans no actions. A vCard with an unlisted number is not
  deleted or banned.
- Shadow mode: no write calls at all, including reviews. The verdict and the stored detection have
  mode `shadow` and list the would-be actions (delete, ban). No ban is recorded.
- Paused mode: no write calls. Admins and the bot are never deleted or removed.
- Silent: nothing is ever sent to a protected group. Reviews go to `Settings.ReviewGroup`.
- A redelivered event (same group and message ID) leads to exactly one Revoke and one Remove.
**Public surface:**
- `internal/pipeline`: `Mode{Enforce,Shadow,Paused}`, `Band{Clean,Certain,Uncertain,StillUncertain}`,
  `Source{None,Known,Rules,AI}`, `Route{None,AutoBan,Ask,DeleteOnly,Allow,Policy}` (the §14
  `detections.route` values), `ActionKind{Delete,Ban,Review}`, `Verdict{Group, Message, Sender, Mode,
  Band, Source, Route, Actions, Explanation}`. The builder chooses the production entry point (e.g.
  `(*Pipeline).Process(ctx, …) (Verdict, error)`). The tests don't call it.
- `internal/pipeline/pipelinetest`: `New(t, Options{Start, Bot})` gives a fresh isolated database on a
  shared testcontainers Postgres and fails `t` if Postgres can't start. Methods: `WA() *fake.Client`,
  `Clock() *clock.Fake`, `Bot()`, `AddGroup(Group{JID, Admins, Members, Settings})` (bot is admin; fake
  participants registered), `Join(group, Member{LID, PN})` (new member as of now), `ConfirmSpam(group,
  text)`, `Overturn(group, text)` (retract any corpus entry for it and allow-list its fingerprint),
  `Blacklist(group, e164)`, `Deliver(Message{Group, Sender, SenderPN, ID, Time, Text, VCards}) Verdict`,
  `Detection(group, id) (Verdict, bool)`, `Banned(group, lid) bool`. `Settings{Mode, Preset, Enforcement,
  ReviewGroup}`: zero values mean enforce, standard, and the preset's enforcement mode. `Preset*` and
  `Enforcement*` constants. Deliver builds a real inbox event through the real envelope builder. A
  whatsmeow-built event must come from a helper under `internal/wa/...`, because only that package may
  import whatsmeow. Deliver then drains the due actions, advancing the fake clock no more than
  pacing needs (≤ 60 s per call, so review timeouts never fire). Setup calls may make reads but no
  writes. The harness fails `t` on internal errors.
**Out of scope:** the AI tier (the harness has no AI, so uncertain → still uncertain → admins), review
decisions and timeouts, network bans, lockdown, enrichment, media.

## F-117 Near-duplicate matching against the corpus, T1 (core)
**Goal:** after the fingerprint allow-list check, SimHash ≤ 3 bits **or** MinHash Jaccard ≥ 0.9 to a
confirmed entry is CERTAIN `known` evidence. Looser closeness is a `rules` signal that only sends the
message on to the AI. With the AI off it goes to admins and the message stays.
**Behaviour:** matching runs on normalized text, so zero-width characters, homoglyphs, fullwidth
forms and Arabic tashkeel/tatweel/alef variants of a confirmed message match. A one-word edit of a long
template is certain. A rewrite of a third of the template is loose: no delete, no ban, band
`still_uncertain`, source `rules`, a review Send. A loose match alone must reach `T_review`. A
fingerprint within the certain limits of an allow-listed (overturned) fingerprint never matches.
A retracted entry stops matching. Empty text (no tokens) never matches. The index is safe for
concurrent use.
**Public surface (`internal/detect/neardup`):** `Fingerprint{SimHash uint64; MinHash []uint64}` (Jaccard
estimate = share of equal positions in equal-length signatures; empty MinHash = no tokens),
`Compute(norm) Fingerprint` (deterministic), `Thresholds{SimHashMaxDistance, MinHashMinJaccard,
LooseSimHashMaxDistance, LooseMinHashMinJaccard}`, `DefaultThresholds()` = 3 / 0.9 / 12 / 0.4,
`Thresholds.Validate()` (requires 0 ≤ certain distance ≤ loose distance ≤ 64 and 0 < loose Jaccard ≤
certain Jaccard ≤ 1), `Closeness{None,Loose,Certain}`, `Match{Closeness, EntryID, Distance, Jaccard,
Allowed}`, `NewIndex(th)`, `Add(id, fp)`, `Remove(id)`, `Allow(fp)`, `Match(fp)`. When several entries
match, Certain wins over Loose. The builder wires it as a T1 analyzer (Certain → known signal, Loose →
weighted rules signal) and decides the shingling and the LSH lookup.
**Out of scope:** pHash, global promotion, poisoning guards (v0.2).

## F-089 Replay harness (builder tests)
`internal/replay` plus `antispam replay`: feed stored inbox rows (`--group`, `--since`) or fixture
events (JSONL of `pipelinetest.Message`-shaped records under `testdata/fixtures/replay/`) through the
full pipeline with the fake client. It never touches real WhatsApp and never persists detections,
actions, bans or reviews in the source database. It reports one line per message (group, ID, band,
source, route, actions, mode) and a summary (counts per band, source and route). With two rule or
weight sets, it lists the messages whose verdict differs. It exits non-zero on errors. A test helper
replays a fixture set inside tests. The replay tests run in CI (`make check` integration).

## F-091 Compose, .env.example, README, CONTRIBUTING (builder tests)
`docker compose up -d` starts `bot` and `postgres:16` with healthchecks (bot waits for a healthy
Postgres; Postgres is not exposed). `.env.example` documents every variable the bot reads: DATABASE_URL,
PUBLIC_URL, OPERATOR_PHONES, LOG_LEVEL, CONFIG_FILE, AI_PROVIDER, AI_BASE_URL, AI_MODEL, AI_TIMEOUT,
AI_API_KEY (the name is set by `ai.api_key_env`), plus any others. A test should fail when `config` reads
an undocumented variable. README covers what the bot is, the unofficial-client ban risk (§3), quick start,
and how to **run shadow mode first** in a real group, review what it would have done, then switch to
enforce. CONTRIBUTING covers development with the fake WAClient (no WhatsApp account needed) and the
branch and Conventional Commit rules. CODE_OF_CONDUCT is also included.

**DESIGN.md refs:** §3, §4, §5.1, §7.0–§7.3, §7.5, §8.1–§8.4, §8.6, §8.7, §9.1, §9.2, §9.7, §9.8, §10.4,
§12.1, §12.2, §14, §18, §19.1, §20 (v0.1), §22.

**Assumptions:** (1) "Paused" means no writes at all. (2) Shadow mode sends no reviews either ("act on
nothing"). (3) The loose defaults 12 bits / 0.4 are not in DESIGN. They were chosen so that a related
rewrite is reliably loose, and they can only route to AI or admins. (4) A fingerprint within the certain
limits of an allow-listed one is suppressed (the conservative reading of "the mistake isn't repeated").
(5) A loose match alone must reach `T_review` ("sends the message to the AI"). (6) A ban's Remove may
name the LID or the PN. (7) The admin/bot test checks only for no delete or ban; an admin alert (§8.7)
is allowed. (8) Review count is "at least one"; the content isn't checked. (9) The MinHash estimator
is assumed accurate to about ±0.05 (e.g. ≥ 128 permutations).

## Acceptance tests
`acceptance/pipeline` (integration):
- `TestKnownSpamFromNewMemberDeletedAndBanned`: delete, Remove, active ban, route auto_ban, certain/known.
- `TestShadowModeRecordsButNeverActs`: zero writes; verdict and stored detection mode shadow with delete+ban.
- `TestKnownSpamFromEstablishedMemberDeletedAndReviewed`: delete and review, no Remove, same band/source.
- `TestNormalMessageUntouched`: new and established senders: no writes, no planned actions.
- `TestAskDeleteFirstDeletesAndAsksBan`: Ask admins preset deletes and reviews, never removes.
- `TestAskBeforeActionOnlyReviews`: review only, no delete, no Remove.
- `TestPresetRoutesKnownTextSpamFromNewMember`: Relaxed/Standard/Strict/Ask admins text matrix.
- `TestBlacklistedVCardFromNewMemberDeletedAndBanned`: `waid` and TEL-only cases are known spam; an unlisted number is untouched.
- `TestAdminsAndBotNeverActedOn`: no delete or Remove for admins or the bot.
- `TestPausedModeDoesNothing`: zero writes.
- `TestDuplicateDeliveryIsIdempotent`: one Revoke, one Remove after a redelivery.
- `TestObfuscatedConfirmedSpamIsCertainKnown` (F-117): zero-width, homoglyph, fullwidth, combined, Arabic.
- `TestTrivialEditOfConfirmedTemplateIsCertainKnown` (F-117): a one-word edit → delete + ban.
- `TestLooseNearDuplicateGoesToAdminsMessageStays` (F-117): rules, still_uncertain, review, no delete or ban.
- `TestOverturnedFingerprintNeverMatches` (F-117): an overturned message and an overturned near variant are not acted on.

`acceptance/neardup` (F-117):
- `TestDefaultThresholdsMatchDesign`: 3 / 0.9; loose strictly looser.
- `TestThresholdsValidateRejectsUnsafe`: out-of-range and inverted thresholds are rejected.
- `TestMatchThresholdBoundaries`: SimHash 3/4/12/13 bits and Jaccard 0.90/0.89/0.40/0.39 with controlled fingerprints.
- `TestMatchPrefersCertainEntry`: Certain beats Loose and names the entry.
- `TestAllowListCheckedFirst`: an overturned fingerprint and a near variant are not certain; an unrelated entry still matches.
- `TestRemoveRetractsEntry`: a removed entry stops matching.
- `TestEmptyFingerprintNeverMatches`: zero and empty-text fingerprints never match.
- `TestComputeOnRealText`: identical/one-word edit certain, rewrite loose, unrelated none; deterministic.
- `TestIndexConcurrentUse`: concurrent Add/Match/Allow/Remove under -race.
