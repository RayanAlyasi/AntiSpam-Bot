## 2026-10-17 · F-064..F-075 (WP-H, action queue) · §9.5, §9.7, §10

Conservative readings where DESIGN.md leaves room; each is in the contract `.agent/contracts/F-064.md`.

- **§10.3 sends:** "no identical text twice in a row in different chats" is enforced strictly. A send
  whose only wording equals the previous send's text to another chat waits until a different text
  has gone out, or expires. The queue never invents wording; callers pass `Payload.Variants`.
- **§10.3 / §9.5 sub-budgets:** OTPs and reviews each get a reserve of 2 sends/min (bucket of 1). A
  ready OTP or review may use it to run ahead of P1 and P2 work, never ahead of P0. Beyond the
  reserve they wait at P3 as usual, so reviews can't starve deletions either.
- **§10.4 deadline-aware ordering:** "moved ahead" applies within a priority only, so priorities stay
  strict. "Near the deadline" is 1 h (`UrgentWithin`).
- **§10.4 ordering in a chat:** lockdown first ("one write protects a group better than hundreds of
  deletes"), then deletes newest first, then kicks, then the rest by age.
- **§10.5 breaker:** it closes only by operator action (`Operator.CloseBreaker`), never by itself,
  even when a temporary ban reports an expiry. The kill switch stops everything, P0 lockdowns
  included. Reads (`Executor.Read`) are refused while the breaker is open, during a 429 pause and
  under the kill switch.
- **§10.5 not admin:** the action fails, and the chat's other pending admin-only actions fail
  without being sent, so a bot that lost admin doesn't keep making unauthorized writes.
- **§9.7 silent:** edits and reactions count as posts, like sends. If the group state can't be read,
  the post is refused. Silent mode is checked afresh at execution time, the one choke point every
  post passes.
- **§10.1 crash recovery:** at-least-once. Actions left running by a crash run again, sends included
  (a rare duplicate DM is safer than a lost review item).
- **§10.4 dedupe:** a dedupe key is unique forever, across all statuses. Keys whose repeat is
  legitimate include their cause (`KickKey(group, jid, cause)`).
- **§10.3 slow-down:** a slowed-down bot also gets a proportionally smaller burst. The slowed rate
  and its calm-time marks are persisted, so a restart doesn't reset the bot to full speed. After a
  manual ceiling raise the rate climbs 1/min per 15 calm minutes instead of jumping.
- **§10.1 serial:** reads made through `Executor.Read` share the one-call-at-a-time lock with writes.
- **Default deadlines:** delete = message time + 48 h; edit 15 min (WhatsApp allows ~20);
  optional warning 10 min; lockdown 1 h; everything else 24 h.
- **Dependencies:** `Groups`, `Alerter` and `Auditor` are interfaces in `internal/actions`, so the
  queue logic doesn't wait for the group-state, alerts and audit modules. Adapters come with the
  second wp-h PR.
- **§10.4 batch size per run:** one coalesced run makes at most 4 calls (4 × `max_kick_batch`
  JIDs). It yields earlier, rather than wait, when the next call would have to wait for the bot's
  bucket or the group's per-minute window, so other groups' work gets a turn. A run also stops
  between calls when the kill switch, a pause or the breaker stops it, and drops members whose
  deadline passes. Unfinished members go back to pending with their outcomes so far, so no JID is
  sent twice; a yield or hold-back doesn't use up an attempt.
- **§10.5 temporary ban:** besides opening the breaker, it cuts the rate like a warning sign, and
  the action that hit it retries with the transient backoff and attempt limit, so a lockdown the
  open breaker still allows never hammers a banned account. Opening the breaker by hand cuts the
  rate the same way, so the backlog drains slowly once it's closed.
- **§10.1 candidate window:** the in-memory window is per priority *and chat* (50 each), plus the
  earliest deadlines and newest messages, so a raided group's backlog can't hide other groups'
  work, OTPs, reviews or urgent deletes.
- **§10.3 configuration:** `config.yaml` `pacing` maps onto the executor through
  `actions.ConfigFromPacing`; the slow-down factor (0.25) and recovery step (1/min) are
  configurable there, and validation refuses a factor that wouldn't slow down.
- **§10.5 operator controls:** on Postgres a control change and its audit_log row commit in one
  transaction (`AuditedControl`).
- **§9.7 who is protected (F-075):** the groups table (F-018) isn't in staging yet, so posting
  rules come from the group settings documents: a group with a document is protected (whatever
  its mode), a missing `silent` key counts as silent, a group named as some group's
  `review.review_group` isn't protected, and a group the bot can't place gets no posts at all.
- **§10.1 fencing:** each store instance claims with its own owner token and only that instance
  settles the claim, so an executor that lost its lock mid-call can't overwrite the new owner's
  state. WhatsApp may still see the action twice (at-least-once).
