# F-147 to F-150: dataset import (v0.1.0)

Date: 2026-10-18. Branch `feat/F-147-corpus-import`. One contract for all four features:
`.agent/contracts/F-147.md`.

## Done

- `antispam corpus import <file|-> --scope instance|group:<jid> [--holdout 0.2]
  [--holdout-clusters FILE] [--allow-ham] [--dry-run]` and `antispam corpus remove --import <id>`
  (`cmd/antispam/corpus.go`). `-` reads stdin, for the distroless image (`docker exec -i`). The
  command applies pending migrations like `serve` does.
- `internal/corpusimport` (no I/O): JSONL/CSV parsing and validation with line numbers (F-147);
  normalization and fingerprints through `textnorm.Prepare` + `corpus.FromMessage`, the same path
  as admin confirmations, so text is redacted and numbers are keyed hashes (F-148); in-file
  dedupe (exact after normalization, and neardup's CERTAIN band) with links/numbers/media merged
  into the kept entry; clustering (cluster_id authoritative, otherwise the closest related
  record, loose band included) and a stratified, deterministic cluster split (F-149); ham kept
  apart (F-150); the report.
- `internal/corpusimport/pgimport`: dedupe against the live corpus in the same scope and against
  every earlier hold-out row, the in-memory recall replay, and one transaction for the batch
  row, entries, `eval_corpus` rows and `--allow-ham` fingerprints. `Remove` deletes the batch's
  entries, eval rows, allow rows and rules learned only from it; the batch row stays, marked
  removed.
- `fastlane.HoldoutReplay`: labelled messages through the real engine with the current rules,
  corpus (plus the batch's entries in memory), weights and settings; nothing recorded or sent.
- Migration `00036_corpus_import.sql`: `import_batches`, `eval_corpus`, FK and index on
  `corpus_entries.import_batch_id`, `corpus_allow.import_batch_id`.
- Docs: `docs/CORPUS_FORMAT.md`, README "Importing a spam dataset".

## Checked on the real dataset (aggregates only; the file stays outside the repo)

Latest run (dry run, 320 spam records, 0 rejected): 29 merged as near-duplicates, 196 clusters.
Random split: 252 entries, 39 held out in 39 clusters; recall without the AI tier 0 deleted, 7 to
admins, 32 missed. With the operator's `holdout_clusters.txt`: 223 entries, 68 held out in 55
clusters, 21 to admins, 47 missed. An earlier real import of the 304-record version: re-import
stored nothing, and remove undid the batch. No raw phone number in any stored text (only
`[phone…]` tokens; with no default region, local numbers are masked rather than hashed).

## Follow-ups

- Hold-out campaigns never get a CERTAIN match by construction, so import recall mostly measures
  loose matching and the AI tier; a recall number per band (F-151) will make that visible.
- A ham allow-list only exists per group (`corpus_allow.group_jid` is required), so
  `--allow-ham` is refused for an instance-wide import.
- Planning is O(n²) (8,000 records took about 35 s on a loaded machine); fine for datasets of a
  few thousand, an LSH front end would fix it.
- Two imports run at the same time aren't serialised, so both can store the same records.
- Removing a batch also removes coverage a later batch relied on (its copies of the earlier
  batch were dropped as already in the corpus).
- Pre-existing, `internal/normalize/redact`: `055/123/4567`, `055_123_4567`, `(055) 123-4567` and
  8-digit runs survive redaction.
- No default region is configured anywhere, so local numbers are masked, not hashed, both live
  and in the corpus.
