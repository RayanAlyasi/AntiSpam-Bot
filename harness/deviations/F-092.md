## 2026-10-17 · F-092 (bundle F-092, F-093, F-094, F-095, F-097, F-098, F-100) · §23

- **F-092: no tag-push trigger.** features.json says "release on v* tags"; DESIGN.md §23.10 (the newer, verified spec) runs GoReleaser as the `goreleaser` job of `release.yml` on push to `main`/`release/*`, after release-please created the tag, because a tag made by a workflow token can't start another workflow. Followed §23.10. The "refuse a non-SemVer tag or one not on main/release/*" rule is the job's first step: it checks the tag matches SemVer, exists on the remote, and points at an ancestor of the pushed commit.
- **F-092: GoReleaser uses `GITHUB_TOKEN`** (contents, packages, id-token, attestations), not the App token. The App is only needed where GITHUB_TOKEN can't do the job: creating the tag past the ruleset (release-please) and opening PRs that run CI (back-merge, whatsmeow bump). This is a narrower use of the App's credentials.
- **F-092: syft comes from `anchore/sbom-action/download-syft` v0.24.3 (SHA-pinned)**, an action that isn't in §23.9's table: the archive SBOMs need syft on PATH. Image SBOMs come from BuildKit (`dockers_v2.sbom: true`).
- **F-092: ldflags set `main.version`, `main.commit`, `main.date`**, but `cmd/antispam` doesn't declare them yet (Go code is outside this bundle). The linker ignores `-X` for undefined symbols, so builds work; the values appear once the variables exist (follow-up in harness/progress/F-092.md).
- **F-093: the edge build is a job in `ci.yml`, not a separate `edge.yml`.** It's gated on `make check` and the image build of the same push (`needs: image`), and it reuses their build cache. Edge images aren't signed (§23.4 asks only for the tags).
- **F-094: `bootstrap-sha` is `31e5906` (the parent of the first Go commit `a80a53d`).** The brief said "the first Go commit"; release-please stops *at* the bootstrap commit and excludes it, so pointing at `a80a53d` would drop the Go skeleton's own `feat:` commit from the first changelog. `31e5906` is also exactly §23.3's "last pre-rewrite commit".
- **F-094: `.release-please-manifest.json` starts as `{}`**, so release-please finds no previous release and uses `initial-version: 0.1.0`.
- **F-097: back-merge also runs for `release/*`** (branch `sync/release-X.Y-<tag>`), because §23.12's hotfix path ends with "verify, then back-merge". For `main` the branch is `sync/main-<tag>`, as §23.10 says. The branch is created through the REST API from the released commit, so the job needs no checkout.
- **F-098: the whatsmeow bump uses the release App's token, narrowed to contents and pull-requests write** (as does the back-merge) (environment `release`; scheduled runs use `main`, which the environment allows), because PRs opened with `GITHUB_TOKEN` don't start CI and the required checks would never run. Its title is `build(deps): …`; the PR body tells the maintainer to retitle it `fix: …` when it fixes a protocol break, so it cuts a patch release (§23.8).
- **F-100: the pinned compose example is in `docs/VERSIONS.md`, not a root `docker-compose.yml`.** The deployment compose file belongs to F-091 (wp-l), which pins `ghcr.io/rayanalyasi/antispam-bot:0.1` and `postgres:18`. The docs example matches those pins. DESIGN.md §19.1 says `postgres:16`; 18 follows F-091 and the test compose file (see deviations/F-000.md), so the docs and the real compose file agree.
