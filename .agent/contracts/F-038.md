# F-038: Phone-number extraction to E.164

> Acceptance tests were waived by the user's fast-track decision for v0.1 work package A (this feature isn't core). The builder's table, property and fuzz tests carry the proof, and the judge checks them against this contract.

**Goal:** find phone numbers in text, however they're written, and parse a single number typed into a command, both normalized to E.164 with `github.com/nyaruka/phonenumbers` and the group's default country.

**Behaviour**
- `FindPhones(text, region)` takes raw text and returns each valid number it finds, in order of position, without overlaps, with its E.164 form and byte span in `text`. The span covers the whole written number, including separators, invisibles and number words, so redaction (F-101) can mask it.
- Recognized forms:
  - `+966 55 123 4567`, `00966551234567`, `0551234567` (region `SA`);
  - `(055) 123-4567` and `055.123.4567`;
  - spaced digits (`0 5 5 1 2 3 4 5 6 7`);
  - fullwidth, Arabic-Indic and Persian digits;
  - invisibles inside the number;
  - `wa.me/9665…`;
  - spelled-out digits in English (`zero five five …`, mixable with digits) and Arabic (`صفر خمسة خمسة …`, common spellings).
  
  All give `+966551234567`.
- Only numbers that phonenumbers considers **valid** are returned. False positives that must not be returned: prices (`3000 ريال`, `1,000,000`), dates (`2026-10-17`, `17/10/2026`), times (`12:41`), years, short codes, order numbers that aren't valid numbers, and two separate numbers glued into one (`055 123 4567 or 056 765 4321` gives two results).
- `region` is an ISO 3166-1 alpha-2 code. When it's empty or unknown, only internationally written numbers (`+`, `00`) are found. A leading `00` is always read as the international prefix. National numbers are never guessed without a region.
- `ParsePhone(s, region)` parses one number in any of the forms above (a whole command argument). It returns its E.164 form, or an error wrapping `ErrInvalidPhone` for anything that isn't exactly one valid number. Invalid input is reported, not dropped (§9.8).
- Never panics. Each E.164 result matches `^\+[1-9][0-9]{6,14}$`. 64 KiB of hostile digits and separators finish in under 3 s with `-race`.

**Public surface:** package `internal/normalize`:
- `type Phone struct { E164 string; Start, End int }` (byte offsets into the input);
- `func FindPhones(text, region string) []Phone`;
- `func ParsePhone(s, region string) (string, error)`;
- `var ErrInvalidPhone error`.

**Out of scope:** attaching phones to the envelope (F-039), WhatsApp registration lookups, blacklist storage and commands, display masking (`+966 5•• ••• •12`), number words beyond 0–9 (`twenty`, `مية`).

**DESIGN.md refs:** §7.2 step 7, §9.8.

**Assumptions**
- Phones aren't a `Result` field (F-034 anticipated one). `Text` takes no region, and adding one would make every normalization depend on group settings. Callers call `FindPhones` with the group's region instead.
- Requiring validity rather than mere "possible" length is the conservative choice. An advertised number in an unexpected format may be missed, but no price or date ever becomes a "known spam number".

**Proof (builder tests):** table tests for each form and each false-positive class, region empty/unknown, `ParsePhone` errors, span correctness (`text[Start:End]` contains the written number); fuzz (no panic, spans in bounds, ordered, non-overlapping, valid E.164).
