# F-020 (+ F-021, F-022): persons, identities, merge and recycled numbers

**Goal:** Map any person JID to one internal person (LID primary, PN when known), record phone
numbers only from free sources (F-021), and merge/back-fill on resolution while never carrying a
recycled number's history to its new owner (F-022).

**Behaviour**
- Every person has a non-zero `PersonID`. JIDs are stored non-AD: `123:5@lid` and `123@lid` are one identity; `Person.LID`/`PN` are normalized, empty when unknown.
- Non-person JIDs (empty, `@g.us`, `@newsletter`, `@broadcast`, no server, empty user) → `ErrNotPerson` from `Ensure`/`Learn`; `MatchPerson` returns not-found, nil error. Same digits on another server never match a person.
- `MatchPerson` is a pure lookup by LID or PN alone (open links only): never creates, never calls `LIDStore`.
- `Ensure` finds or creates; idempotent, including under concurrent calls for one JID.
  - LID-only: may call local `PNForLID` (PN row source `lid_store`); never calls `LIDForPN`.
  - New PN-only: calls `LIDForPN` exactly once; if a LID comes back it becomes primary, and an existing LID person is reused. No further `LIDForPN` for that PN on repeat `Ensure` (resolved or not, at the same instant). A lookup error still yields the PN-only person, no error.
- `Learn(lid, pn, src)`: requires a LID then a PN and a known `Source`, else error and nothing written. Never calls `LIDForPN`. Rows carry `src`; PN rows carry the country code (nyaruka/phonenumbers: 9665… → "966", 44…, 1…, 20…); LID rows have none.
- `Resolved` fires exactly once each time a PN becomes newly linked to a person with a LID (new pair, PN added to LID person, PN-only person given its LID, `Ensure` lookup hit). Repeats emit nothing and add no rows.
- Merge: PN-only person + separate LID person → LID person keeps its ID and gains the PN; memberships move (shared groups once); the PN-only record is no longer returned by `MatchPerson`/`Ensure`; `Resolved.MergedFrom` = merged-away ID; the merge is recorded (person_merges). PN-only with no LID person → same record gains the LID, `MergedFrom` 0.
- Recycled: known PN (open link to LID A) learned with LID B → old PN row kept with `ValidTo = clock.Now()`; PN linked open to B's person (existing or new); persons never merged; memberships do not move; `MatchPerson(A)` still returns the old person, whose `PN` is no longer the recycled number; exactly one `RecycledNumber{PN, OldLID, OldPerson, NewLID, NewPerson}`; **no** `Resolved`. Repeat → no second event.

**Public surface** (`internal/identity`): `PersonID`, `Person{ID,LID,PN}`, `Source` + `SourceSenderAlt|Participant|Event|LIDStore|DM|SelfVCard|Usync`, `Kind` + `KindLID|KindPN`, `Identity{Kind,Value,Source,CountryCode,ValidTo *time.Time}`, `LIDStore`, `Events`, `ResolvedEvent{Person,PN,MergedFrom,Source}`, `RecycledEvent`, `ErrNotPerson`, `Store`, `NewMemoryStore() Store`, `New(Store, LIDStore, Events, clock.Clock) *Service`, `(*Service)` `MatchPerson`, `Ensure`, `Learn`, `Identities`, `AddMember(ctx, group, PersonID) error`, `GroupsOf(ctx, PersonID) ([]wa.JID, error)`. Stub: `internal/identity/identity_stub.go` (replace it). `Store` methods are the builder's choice.

**Out of scope:** Postgres store and migrations; moving strikes, detections, bans, corpus, spammer data (later features hook `Resolved`); back-fill jobs, identity_watch, audit log rows; self-vCard confirmation; usync batching/pacing (behind `LIDStore`); a LID changing its PN (unspecified).

**DESIGN.md refs:** §7.7, §14 (persons, identities, person_merges, members).

**Assumptions (conservative readings)**
- Recycled numbers emit no `Resolved`: back-fill would apply number-based bans/watch rules to the new owner.
- A PN lookup failure is not an `Ensure` error (DESIGN: the record works without the missing identifier).
- An unresolved PN is not re-looked-up per message; a later time-based retry is allowed but not tested.
- Unknown `Source` values are rejected (§14 lists a closed set).

**Acceptance tests** (`acceptance/identity/`)
- `TestMatchPersonFindsByEitherIdentifier`: LID or PN alone finds the person with both fields.
- `TestMatchPersonNormalizesDeviceSuffix`: `:N` device forms match and don't create duplicates.
- `TestMatchPersonNeverCreatesOrLooksUp`: no creation, zero LIDStore calls.
- `TestNonPersonJIDsAreRejected`: ErrNotPerson / not-found for groups, channels, broadcast, malformed.
- `TestEnsureIsIdempotent`: same ID on repeat and under 16 concurrent calls.
- `TestEnsureLIDOnlyUsesOnlyLocalLIDStore`: PN from local store with source lid_store; no LIDForPN.
- `TestEnsurePNOnlyLooksUpLIDOnce`: one LIDForPN, LID becomes primary, no repeat lookup.
- `TestEnsurePNOnlyUnresolvedDoesNotRepeatLookup`: 6 Ensures → 1 lookup.
- `TestEnsurePNLookupFailureStillCreatesPerson`: lookup error still yields PN-only person.
- `TestEnsurePNResolvesToExistingLIDPerson`: PN resolves to the existing LID person, one Resolved.
- `TestLearnRecordsSourceOnIdentityRow`: each of the 7 sources lands on the PN row (open).
- `TestLearnDerivesCountryCode`: 966/44/1/20 on PN rows, none on LID rows.
- `TestLearnRejectsSwappedPairOrUnknownSource`: errors, nothing created.
- `TestLearnNewPairEmitsResolvedOnce`: one Resolved (no merge), idempotent rows.
- `TestLearnAddsPNToLIDPerson`: PN joins existing LID person, Resolved without merge.
- `TestLearnNeverCallsLIDForPN`: zero LIDForPN across learns, incl. recycle.
- `TestAddMemberIsIdempotent`: one membership per group.
- `TestLearnGivesPNOnlyPersonItsLID`: PN-only record keeps ID and gains LID.
- `TestLearnMergesPNOnlyPersonIntoLIDPerson`: merge moves memberships, MergedFrom set, idempotent.
- `TestRecycledNumberClosesOldLinkAndNeverMerges`: valid_to set, no merge, no Resolved, one flag.
- `TestRecycledNumberIsIdempotent`: one RecycledNumber, no duplicate rows.
