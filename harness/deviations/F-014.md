## 2026-10-17 · F-014, F-015, F-033 · §5.1, §14, §15

- **The inbox dedupe key adds the sender and the row kind**: `UNIQUE (chat, sender, msg_id, edit_seq, kind)` instead of §14's `(chat, msg_id, edit_seq)`. Message IDs are chosen by the sending client, so without the sender a spammer reusing a member's recent ID would be deduplicated away and never moderated; without the kind an undecryptable event would block the decryptable copy whatsmeow's retry delivers later. `edit_seq` holds whatsmeow's edit attribute.
- **The inbox writes a base message_index row** (sender, time, verdict clean) for each moderated group message, so F-033 holds before detection lands; detection later fills in fingerprints and raises the verdict, and a partial write never erases a fuller one.
- **Claims are leases, not held row locks.** Workers pick rows with `FOR UPDATE SKIP LOCKED` and stamp `claimed_until` (5 minutes), then process outside the transaction. Holding the lock for the whole pipeline (which may call the AI) would pin a transaction per row. A crashed worker's rows return when the claim expires.
- **Retries:** backoff `min(2^n · 2 s, 5 min)`, given up after 5 attempts, the error kept in `last_error`.
- **Routing in the workers role reads roles from the members table** (refetched once a minute) instead of the connector's in-memory participant cache, so the workers role works in a process without a WhatsApp connection (§15).
- **message_index never lowers a verdict (clean < policy < spam) or shortens an expiry** on a later write (an edit re-analysed as clean keeps the spam row for 30 days).
- **`inbox_retention` is an hourly River job** that purges both the inbox (72 h) and expired message_index rows.
