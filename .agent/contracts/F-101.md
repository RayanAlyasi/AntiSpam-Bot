# F-101: Shared redaction helper

> Acceptance tests were waived by the user's fast-track decision for v0.1 work package A (this feature isn't core). The builder's table, property and fuzz tests carry the proof, and the judge checks them against this contract.

**Goal:** one function that makes text safe to store or show: it masks third-party phone numbers, emails, mentions and names, keeps the spam's own advertised numbers only as keyed hashes, and truncates. The corpus (§7.5), reviews (§9.5) and the AI context (§7.4) all use it.

**Behaviour**
- Phone numbers found by `normalize.FindPhones(s, o.Region)` (any written form, including spelled-out and Arabic digits) are replaced over their whole span:
  - with `[phone:<id>]` when their E.164 is in `o.Advertised` and `o.Key` is non-empty, where `<id>` is the first 12 characters of `PhoneHash(o.Key, e164)`;
  - with `[phone]` otherwise.
  
  The same number in two formats gives the same token, and a different key gives a different token.
- Also masked:
  - any other run of 9 or more digits (ASCII or Arabic-Indic, with single spaces, `-` or `.` between) becomes `[phone]`, so numbers from other regions don't leak;
  - email addresses, including `mailto:`, become `[email]`;
  - `@` followed by 6 or more digits (WhatsApp mentions) becomes `[mention]`;
  - each name in `o.Names` (whole word, case-insensitive, names under 2 runes ignored) becomes `[name]`.
  
  Invisibles or fullwidth characters inside any of these don't stop masking.
- Everything else stays as written. Prices, dates, short numbers and URLs are kept (`3000 ريال`, `2026-10-17`, `bit.ly/x`).
- `o.MaxRunes > 0` truncates **after** masking, to at most `MaxRunes` runes including a trailing `…`. Truncation never cuts inside a placeholder (a partial placeholder is dropped), a rune or a combining sequence. `MaxRunes == 0` means no limit.
- Output is valid UTF-8 (invalid bytes become U+FFFD). Redaction is idempotent: placeholders are never re-masked. It never panics, and 256 KiB of input finishes in under 3 s with `-race`.
- `PhoneHash(key, e164)` returns the lowercase hex HMAC-SHA256 of the E.164 string, so stores can match `waid` numbers (§7.5) without keeping them. The key always comes from the caller, and the package reads no config.

**Public surface:** package `internal/normalize/redact` (new):
- `type Options struct { Region string; Key []byte; Advertised []string; Names []string; MaxRunes int }`;
- `func Text(s string, o Options) string`;
- `func PhoneHash(key []byte, e164 string) string`.

**Out of scope:** deciding which numbers are advertised (the caller passes them, e.g. the spam message's own `FindPhones` results), key management and rotation, display masking of the sender (`+966 5•• ••• •12`), detecting names not passed in, obfuscated emails (`ali [at] gmail`), the arch-map addition for `review`/`store`.

**DESIGN.md refs:** §7.5 (retention: what is masked and what is hashed), §9.5 (review text, ~300 characters), §7.4 (context bundle masking), §17.

**Assumptions**
- With an empty key, advertised numbers are masked rather than hashed, because a hash under an empty key can be reversed by brute force.
- The 9-digit fallback masks a few long non-phone numbers. Over-masking is the safe failure for privacy.

**Follow-up (not a blocker):** `review` and `store` will import `internal/normalize/redact`, so `harness/proposed/.go-arch-lint.yml` needs `normalize` in their `mayDependOn` before it's activated. `ai` already has it.

**Proof (builder tests):** table tests for each masked kind and form, advertised vs third-party, key-dependence, kept non-cases, truncation boundaries; fuzz (no panic, valid UTF-8, idempotent, length bound, and no `FindPhones` hit or email left outside placeholders).
